# HslCommunication S7 通信机制与 PIDTuner 对比研究

更新日期：2026-08-19

## 2. V7.0.1 的通信底层机制

### 2.1 协议与连接

`SiemensS7Net` 基于 Socket 直接实现 Siemens S7 over ISO-on-TCP。建立连接时完成 TCP 连接、COTP 连接确认和 S7 会话初始化，之后通过 `ReadFromCoreServer` 完成一次请求/响应交互。

库同时支持两种连接模式：

- 短连接：每次读取时连接，读取完成后关闭。
- 长连接：调用 `ConnectServer()` 或 `SetPersistentConnection()` 后复用 Socket，最后调用 `ConnectClose()`。

长连接减少握手和 Socket 建立开销，适合高频轮询，但不改变 PLC 与 PC 两套时钟相互独立的事实。

### 2.2 请求串行化

网络基类在 `ReadFromCoreServer` 外围使用 `InteractiveLock`。同一个通信对象被多个线程调用时，请求、发送、接收和响应解析被串行化，避免多个 S7 请求在同一 Socket 上交叉并导致响应错配。

这个锁解决的是“同一连接的并发安全”，不是采样线程的周期精度。锁竞争严重时，它反而可能增加排队延迟，因此采集系统仍应保持单一连接所有者和单一采集循环。

### 2.3 多点读取

V7.0.1 提供 `Read(string[] address, ushort[] length)`：

1. 将地址解析为 `S7AddressData[]`。
2. 单个 S7 ReadVar 请求最多携带 19 个地址项。
3. 超过 19 项时分组，并按组顺序读取。
4. 单地址长度超过 200 字节时再拆分读取。

它采用的是“一个 ReadVar 请求携带多个 S7ANY 地址项”，不是按 DB 的最小到最大偏移读取一整段连续字节。

### 2.4 错误与重连

底层统一使用 `OperateResult` 返回成功状态、错误码和错误消息。长连接发生 Socket 错误后会标记连接异常，后续交互可以重新获取或建立可用 Socket；短连接则天然每次重新建立通道。

这种设计提高了现场网络异常下的可恢复性，但重连会产生明显的长尾读延迟。它应被诊断为连接事件，不能混入普通采样抖动统计。

## 3. 与 PIDTuner 当前实现的差异

| 维度 | HslCommunication V7.0.1 | PIDTuner 当前实现 |
| --- | --- | --- |
| TCP/S7 会话 | 支持短连接和显式长连接 | 实时采集启动时建立一次会话并持续复用 |
| 并发保护 | 通信对象内部使用交互锁 | 当前由单采集循环隐式保证串行，无客户端级锁 |
| 多点读取 | 每请求最多 19 个 S7ANY 地址项 | 同一 DB 按覆盖范围聚合为连续块读取 |
| 同帧一致性 | 同一 ReadVar 响应包含多地址项，但不证明跨 PLC 扫描原子性 | 同一 DB 的点位来自同一块响应，帧内一致性更强 |
| 大请求拆分 | 19 项和 200 字节规则 | 固定批次及 DB 覆盖范围规则 |
| 调度时钟 | 通信库不负责固定周期调度 | `Stopwatch` 锚定计划时刻，超期后跳过错过帧 |
| 诊断 | 以操作结果和错误信息为主 | 记录计划、请求、响应、缓存、UI 时间及相位指标 |
| UI 解耦 | 不涉及 | 采集写缓冲，UI 按独立刷新周期消费 |
| 故障恢复 | 基类提供异常连接恢复路径 | 会话内缺少完整自动重连状态机 |

对当前三个同 DB 点位的场景，PIDTuner 的连续 DB 块读取并不弱于 V7.0.1 的多地址 ReadVar。它只发送一个 S7 请求并从同一响应解码三个点位，对一致性尤其有利。

## 4. 值得学习的设计

### 4.1 客户端边界的通信互斥

即使当前实时采集只有一个调用者，也应在 S7 会话或客户端边界明确限制“一个连接同一时刻只有一个未完成请求”。这样未来加入检查通信、后台历史补采等功能时，不会意外共享 Socket 并交叉收包。

建议优先采用单一连接所有者或异步互斥，而不是让多个业务线程直接调用客户端。

### 4.2 显式连接状态机

可将连接状态明确为：`Disconnected`、`Connecting`、`Ready`、`Degraded`、`Reconnecting`、`Stopped`。重连次数、重连耗时和重连后的首帧应单独记录，避免污染普通 `readDuration` 分布。

### 4.3 PDU 能力驱动的拆分

PIDTuner 目前的固定项数和连续 DB 覆盖范围应进一步受协商 PDU 长度约束。稀疏地址之间距离很大时，不应为了“一次读取”而构造过大的连续区域；应按 PDU、空洞成本和点位数量共同分组。

### 4.4 请求与响应关联校验

应校验响应中的 S7 PDU reference 是否与请求一致，并在诊断中记录不匹配、迟到响应和意外报文。当前单请求串行降低了风险，但协议边界仍应自证正确。

### 4.5 统一错误分类

借鉴 `OperateResult` 思路，将失败分为连接、握手、发送、响应头、响应体、S7 返回码、解析和取消。这样可以区分 PLC 慢响应、网络断连和本地调度延迟。

## 5. HslCommunication 是否存在相位混淆

结论：**会出现，但这不是 HslCommunication 独有的协议缺陷。**

V7.0.1 的读取模型仍是 PC 主动轮询。它没有提供以下机制：

- PLC 周期与 PC 采样周期的公共时钟；
- PLC 侧样本序号或采样时间戳；
- PLC 扫描完成事件触发；
- 硬件时间同步或确定性实时调度；
- 对 PLC 更新相位进行锁定的闭环控制。

假设 PLC 名义上每 100 ms 更新一次，PC 也名义上每 100 ms 请求一次。只要两者实际周期存在微小频差，或者网络、PLC 通信任务、操作系统调度存在抖动，PC 的读取时刻就会逐渐穿过 PLC 更新边界。结果是某些周期读到两次相同值，另一些周期跨过一个值，形成重复点、跳点和周期性锯齿。这正是拍频/相位漂移的表现。

长连接、批量读取和通信锁能够：

- 降低平均请求耗时；
- 减少握手引入的随机抖动；
- 改善一帧内多个点位的一致性；
- 避免并发请求导致响应错配。

但它们不能保证每次请求都落在 PLC 更新后的固定相位。因此，换成 HslCommunication 不会从根源上消除相位混淆。

## 6. 对 PIDTuner 的直接结论

1. 不建议仅为相位问题替换现有 S7 客户端。当前长连接、DB 聚合和锚定调度已覆盖 HSL 最关键的性能思路。
2. 最值得吸收的是通信互斥、连接状态机、PDU 驱动拆分、响应关联校验和错误分类。
3. 这些改进主要降低通信异常和长尾抖动，不能建立 PLC/PC 时钟同步。
4. 若 PLC 侧不增加序号或时间戳，软件只能缓解：提高采样率后重采样、估计 PLC 更新相位、识别重复/跳变样本、显示原始值与重建值。
5. 若要求每个显示点严格对应 PLC 的一次更新，必须引入 PLC 侧样本序号/时间戳、事件触发采集，或工业时钟同步；仅靠普通 S7 轮询无法证明这一点。

## 7. 推荐后续验证

在不更改 PLC 程序的前提下，可先做 A/B 实验：

- 保持当前 DB 聚合读取和长连接。
- 同时记录计划时刻、请求时刻、响应时刻、读取值及 PDU reference。
- 分别以 80 ms、100 ms、120 ms 轮询同一固定周期信号。
- 统计重复值长度、跳变量、读耗时长尾和波形异常的周期。

若 100 ms 采样出现明显周期性重复/跳点，而 80 ms 过采样后重采样显著改善，就能进一步确认主因是异步时钟拍频，而不是 S7 报文解析或 UI 绘图错误。

## 8. 已确认的下一步改进策略

以下两项已于 2026-08-20 确认为后续通信改进内容：

1. **PDU 能力驱动的拆分**：读取会话保存 S7 Setup Communication 协商得到的 PDU 长度；按响应负载、地址项开销、DB 空洞成本和点位数量共同规划读取块，不再只依赖固定项数或最大连续覆盖范围。
2. **统一错误分类**：建立稳定的错误类别、错误码和诊断上下文，至少区分连接、握手、发送、响应头、响应体、S7 返回码、解析、超时、取消和重连；长期统计按类别聚合，不让重连或配置错误污染普通读取耗时分析。

这两项用于改善通信效率、可诊断性和长期可维护性，不将其表述为 PLC/PC 相位同步方案。
